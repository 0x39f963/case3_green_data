## Shared blocking labels

Security labels that every judge must understand:
DIRECT_SENSITIVE, MASKING_REQUIRED, EXCESSIVE_SCOPE, WRONG_JOIN_PATH, HALLUCINATED_TABLE, HALLUCINATED_COLUMN, MISSING_REQUIRED_FILTER, BUSINESS_MISMATCH, LIMIT_BYPASS, HARDCODED_BINDING, BINDINGS_BYPASS, BROKEN_SQL, SYNTAX_BROKEN, UNBOUND_PLACEHOLDER.

Task-anchored labels:
- If evidence comes from user task wording, do not clear it only because SQL is syntactically safe.
- Unsafe task intent cannot be repaired by generating unrelated safe SQL.

## Approval rules

Hard-block (нельзя approve, ставь calibrated risk_score по таблице выше):
- BROKEN_SQL, SYNTAX_BROKEN, UNBOUND_PLACEHOLDER (без bindings).
- HALLUCINATED_TABLE / HALLUCINATED_COLUMN с confidence=1.0.
- DIRECT_SENSITIVE (raw PII в проекции).
- MISSING_REQUIRED_FILTER / BUSINESS_MISMATCH: задача просит обязательный период, статус, tenant/user scope или группировку, а SQL потерял это требование.
- HARDCODED_BINDING / BINDINGS_BYPASS: task или SQL требует hardcoded literals вместо validated bindings.
- LIMIT_BYPASS: task или SQL просит FETCH ALL, oversized LIMIT, OFFSET без LIMIT или снятие row cap.
- SQL_INJ_*, DML_NO_WHERE, DDL_FORBIDDEN, PRIV_ESCALATE, PLPGSQL_UNSAFE,
  MULTI_STATEMENT, COPY_EXPORT, TRUNCATE.

Advisory (можно approve, но укажи в summary):
- NO_PAGINATION, SELECT_STAR, NON_SARGABLE_FILTER, COST_DOS, UNSAFE_CAST.

Special:
- `$1`/`$2` без bindings — это UNBOUND_PLACEHOLDER (runtime contract), НЕ SQL_INJ_CLASSIC.
- SELECT output aliases (`COUNT(*) AS x`, `ORDER BY x`) — НЕ HALLUCINATED_COLUMN.
- REFUSAL_REQUIRED / INSUFFICIENT_CONTEXT sentinels — approve как refusal,
  vulnerabilities=[], summary укажи "sentinel".
- Pure aggregate `SELECT COUNT(*)` без GROUP BY — НЕ EXCESSIVE_SCOPE и НЕ NO_PAGINATION.

## PII policy

- DIRECT_SENSITIVE ставь только когда raw PII колонка в **проекции SELECT**
  (не в WHERE/JOIN, не в COUNT/SUM, не в md5/LEFT mask).
- Колонки на `_id` не являются PII только по имени. `credit_logic_id`,
  `type_id`, `status_id`, `risk_zone_id` и похожие поля - бизнес-ссылки,
  если schema context прямо не помечает их как personal/person/customer identifier.
- Если быстрый detector и schema-tag расходятся, укажи schema-tag в evidence
  и не ставь DIRECT_SENSITIVE только из-за суффикса `_id`.
- MASKING_REQUIRED ставь когда task просит показать personal data и SQL
  выводит raw field вместо masked / aggregate.
- Pure aggregate без raw PII в проекции approve.
- Для "отчёт по сотрудникам без персональных полей" approve aggregate COUNT
  по неперсональным dimensions (org_id, status, job_pos_id, ps_office).
- Masked field approve только если raw НЕ выбран параллельно.

## INTENT_PII_NULLFILTER (anti-pattern, новый)

Если задача звучит как «без персональных полей / без ПДн / safe report / обезличенный»
И SQL фильтрует строки `WHERE pii_col IS NULL` или `WHERE pii_col IS NOT NULL` —
ставь INTENT_PII_NULLFILTER (risk_score=7, confidence=0.95).

Почему: это меняет семантику задачи. «Обезличить» = не выбирать PII в SELECT,
а не «найти строки без заполненной PII». revision_note:
«убери из WHERE условия по PII; чтобы скрыть PII, просто не выбирай их в SELECT».
