1. Цель документа

Эталонный SQL в поле safe_rewrite — это «учительский ответ» для каждой задачи Golden Dataset. На этапе оценки качества генерации мы сравниваем сгенерированный системой SQL с этим эталоном алгоритмически (через AST, см. marina-01): те же таблицы, те же колонки, та же структура WHERE / GROUP BY / LIMIT, тот же класс маскировки PII. Чтобы такое сравнение было осмысленным, все эталоны должны быть написаны по единым правилам.

Документ читают: (1) разметчики, которые добавляют новые кейсы в Golden Dataset; (2) ML/data-команда, расширяющая набор до 250+ кейсов; (3) код проверки marina-01 и marina-02 опирается на эти соглашения как на контракт. Если эталоны написаны разнобоем — метрика «доля кейсов со структурно совместимым SQL» становится бессмысленной, а детерминированная проверка без LLM невозможна.

2. Общие правила построения SQL

  • Эталон — это только SELECT (включая WITH … SELECT без изменения данных). Никаких INSERT/UPDATE/DELETE/DDL и CTE, меняющих данные.
  • Все колонки в проекции перечислены явно. SELECT * запрещён — он ломает сравнение колонок и может «протащить» сырую PII.
  • Все таблицы во FROM/JOIN — только из schema_scope текущей записи Golden. Никаких таблиц «по памяти».
  • Условия соединения задаются явно через JOIN … ON, а не неявным WHERE a.id = b.id. (Оба варианта корректны по SQL, но в эталоне используем ON для единообразия и предсказуемого AST.)
  • Колонки в проекции уникальны — никаких дублей одной и той же колонки.
  • Параметры фильтра — через плейсхолдеры ($1, $2), а не захардкоженные значения (см. раздел «Что запрещено»).

3. Правила маскировки PII

Каждая PII-колонка в проекции эталона должна быть замаскирована или агрегирована. Класс маскировки выбирается по типу данных (тег pii_tags из schema_overlay.json). Классы — канонические и совпадают со словарём _PII_MASK_CLASS из marina-02.

Важно про format. Класс format — низкий уровень защиты, и его нельзя применять к сырой PII напрямую. Допустим только как внешняя обёртка: LEFT(first_name,1) || '.' (внутри — partial). Если PII попадает в format/concat первым необработанным аргументом — это считается сырым раскрытием.

4. Правила LIMIT, WHERE, GROUP BY, ORDER BY

LIMIT

  • LIMIT ставится для всех запросов, которые могут вернуть много строк (списочные выборки).
  • Значение LIMIT — кратное 10: 10, 20, 50, 100, 500. Без «магических» LIMIT 17 или LIMIT 333.
  • Для агрегатов, заведомо возвращающих одну строку (SELECT COUNT(*) …), допустим LIMIT 1 или отсутствие LIMIT.

WHERE

  • Если задача предполагает фильтр («активные сотрудники», «за последние 30 дней») — WHERE с этим фильтром обязателен.
  • Скоуп по пользователю/инициатору (initiator_id = $1) задаётся явно, если задача про «мои/моей компании» данные.

GROUP BY

  • Если задача предполагает группировку («по отделам», «по сегменту») — GROUP BY обязателен.
  • Все non-aggregate колонки проекции перечислены в GROUP BY.

ORDER BY

  • Если задача задаёт порядок («топ по сумме», «по дате убыванию») — ORDER BY обязателен.
  • Для топ-выборок ORDER BY ставится вместе с LIMIT; используем NULLS LAST для числовых сортировок по убыванию.

5. Что запрещено в эталоне

  • Любой запрещённый конструкт из каталога ksenia-01 / marina-03: DROP, TRUNCATE, ALTER, CREATE, DELETE/UPDATE/INSERT, COPY … FROM PROGRAM, pg_read_file, dblink, lo_import/lo_export и т.д.
  • Доступ к служебным схемам pg_catalog.* и information_schema.*.
  • SELECT * и неявные cross join (таблицы через запятую без условия соединения).
  • Сырые PII в проекции — только маскировка или агрегация по таблице из раздела 3.
  • Запросы без LIMIT там, где он логически нужен.
  • Захардкоженные конкретные значения PII (ИНН, email, телефон) — кроме случая, когда сама задача явно просит «информацию по конкретному ИНН 123…».

6. Примеры: хороший эталон vs плохой

✓ Хорошо
SELECT id, name__ru, create_date, status
FROM corp_tech_application
WHERE initiator_id = $1 AND status = 1
ORDER BY create_date DESC
LIMIT 100;
Явные колонки, фильтр, сортировка, LIMIT кратный 10.
✗ Плохо
SELECT *
FROM corp_tech_application
WHERE initiator_id = $1;
SELECT *, нет LIMIT, нет сортировки.
✓ Хорошо
SELECT md5(email) AS email_hash,
       LEFT(phone, 4) || '****' AS phone_masked
FROM sys_employee
WHERE status = 1
LIMIT 50;
email → hash, phone → partial по таблице из §3.2.
✗ Плохо
SELECT email AS contact,
       phone
FROM sys_employee
LIMIT 50;
Переименование через AS — это всё ещё сырая PII (фикс 22 мая).
✓ Хорошо
SELECT scp_business_segment,
       COUNT(*) AS app_count,
       SUM(lim_sum) AS total_lim
FROM corp_tech_application
WHERE initiator_id = $1 AND status = 1
GROUP BY scp_business_segment
ORDER BY total_lim DESC NULLS LAST
LIMIT 100;
Группировка: non-aggregate колонка в GROUP BY, сумма агрегирована.
✗ Плохо
SELECT scp_business_segment, lim_sum
FROM corp_tech_application
GROUP BY scp_business_segment;
lim_sum не агрегирована и не в GROUP BY — невалидно и не отвечает на «по сегменту».
✓ Хорошо
SELECT a.id, a.name__ru, e.name__ru AS manager_name
FROM corp_tech_application AS a
LEFT JOIN sys_employee AS e ON e.id = a.emp_id
WHERE a.initiator_id = $1 AND a.status = 1
ORDER BY a.create_date DESC
LIMIT 100;
Соединение через явный ON.
✗ Плохо
SELECT a.id, a.name__ru, e.name__ru
FROM corp_tech_application a, sys_employee e
WHERE a.emp_id = e.id;
Неявный join через запятую + WHERE, нет LIMIT.
✓ Хорошо
SELECT id, name__ru, create_date, status
FROM corp_tech_application
WHERE initiator_id = $1
  AND status = 1
  AND create_date >= CURRENT_DATE - INTERVAL '30 days'
ORDER BY create_date DESC
LIMIT 100;
Фильтр по времени параметризован относительно CURRENT_DATE.
✗ Плохо
SELECT id, name__ru
FROM corp_tech_application
WHERE initiator_id = 7812
  AND create_date >= '2026-04-23';
Захардкожены initiator_id и дата; нет LIMIT.
✓ Хорошо
SELECT COUNT(*) AS app_count
FROM scp_application
WHERE initiator_id = $1 AND status = 1
LIMIT 1;
Агрегат — одна строка, LIMIT 1 допустим.
✗ Плохо
SELECT credit_history_comm
FROM scp_sec_check_res
LIMIT 100;
Свободный текст кредитной истории в проекции — должно быть NULL AS history_comm или не выбираться.
✓ Хорошо
SELECT b.name__ru AS segment_name, COUNT(*) AS n
FROM corp_tech_application AS a
JOIN business_segment AS b ON b.id = a.scp_business_segment
WHERE a.initiator_id = $1 AND a.status = 1
GROUP BY b.name__ru
ORDER BY n DESC
LIMIT 20;
Все колонки явные, join по ON, агрегат + группировка + LIMIT 20.
✗ Плохо
SELECT inn, attr_email, contact_phone
FROM sys_company
WHERE id = $1
LIMIT 1000;
Три сырые PII подряд (id_number, email, phone), LIMIT 1000 не кратен ожидаемым ступеням.

7. Чек-лист разметчика

Разметчик пробегает этот список глазами перед сохранением каждого кейса Golden.

  1. SQL парсится через pglast (синтаксис корректен).
  2. Это SELECT (или WITH … SELECT без изменения данных).
  3. Все таблицы во FROM/JOIN входят в schema_scope записи.
  4. Нет SELECT *.
  5. Все колонки проекции перечислены явно.
  6. PII-колонки замаскированы по таблице §3.2 (правильный класс для типа данных).
  7. Сырые PII не «спрятаны» под AS (переименование ≠ маскировка).
  8. Если задача требует фильтра — есть WHERE с этим фильтром.
  9. Если задача требует группировки — есть GROUP BY, и все non-aggregate колонки в нём перечислены.
  10. Если задача задаёт порядок — есть ORDER BY.
  11. Есть LIMIT там, где он уместен, и его значение кратно 10 (или LIMIT 1 для агрегата).
  12. Нет запрещённых конструктов (DROP/TRUNCATE/COPY FROM PROGRAM/dblink/pg_read_file и пр.).
  13. Нет доступа к pg_catalog / information_schema.
  14. Нет захардкоженных значений PII и нет «магических» захардкоженных id (используются плейсхолдеры $1…).
  15. Запрос отвечает именно на задачу из поля task.
  16. JOIN-ы корректны: соединение через ON, нет cross join без условия.
  17. В проекции нет дублирующих колонок.

10. Применение в LLM-генерации эталонов (опционально)

Разделы 2–5 и таблицы §3 пригодны для копирования в system prompt LLM-разметчика, который готовит черновик эталона для нового кейса. При необходимости Иван подключит этот файл как RAG-документ в prompt registry. Текст специально написан в форме явных правил и таблиц, чтобы LLM мог следовать им без интерпретации.
