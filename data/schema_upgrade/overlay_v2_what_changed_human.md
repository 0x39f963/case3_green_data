# Что мы улучшили в `schema_overlay_v2.json` — человеческим языком

Этот документ — для ревьюера из соседней ветки. Объясняет, **что именно** поменялось, **почему это важно**, и **какие сценарии** мы починили. Без жаргона.

## В двух словах

`deploy/schema_overlay_v2.json` — это «словарь» для модели генерации SQL. Когда пользователь спрашивает «покажи активные сотрудники», модель не лезет в SQL — она сначала читает overlay и решает: «активные» = `sys_employee.status = 1`. Если в overlay у поля `status` написано просто `"Статус"`, модель не понимает, к чему относится, и часто берёт неправильное поле из другой таблицы.

В v2 при первичной заливке (PR #5) у 116 колонок осталось наследственное короткое описание из исходной БД («Валюта», «Сумма», «Период», «Описание»). Модель видела одно и то же слово в десятках разных таблиц и угадывала.

**Что мы сделали:** прошлись по этим 116 колонкам, переписали `description` так, чтобы в нём явно был указан **объект** (какая таблица / какая сущность) и **назначение** (для каких аналитических вопросов поле используется). Также переписали `nl_phrases` — фразы, по которым FAISS/embed-индекс матчит русский запрос пользователя на это поле.

Структуру (60 таблиц, 1872 колонки), PII-теги, join-keys, allowed/denied операции не трогали.

## Чем это улучшает реальный пайплайн

Пайплайн работает так: **NL-запрос → RAG ищет релевантные таблицы и колонки в overlay → LLM генерирует SQL по выбранному контексту → guard валидирует**.

Слабые места v1, которые мы починили:

### 1. Модель путала одноимённые поля в разных таблицах

В v2 8 разных таблиц имели колонку с `description: "Сумма"` или `description: "Валюта"`. RAG-индекс не мог решить, к какой таблице относится запрос «общая сумма по заявке».

**Пример конкретно:**

| Таблица | Колонка | Было | Стало |
|---|---|---|---|
| `scp_amd_product` | `scp_general_amount` | «Сумма» | «Общая запрашиваемая сумма по продукту РУМ в составе заявки СКП (в рублях). ...» |
| `scp_decision_quest` | `scp_sublimit_sum` | «Сумма» | «Сумма сублимита по продукту в составе вопроса на решение СКП (в рублях). ...» |
| `product_pricing` | `scp_sublimit_sum` | «Сумма» | «Сумма сублимита по продукту в карточке ценообразования (в рублях). ...» |

Теперь когда пользователь спрашивает «общая сумма по продукту в заявке», модель попадает в `scp_amd_product.scp_general_amount`, а не в `scp_decision_quest.scp_sublimit_sum` (это уже частная сумма по сублимиту в вопросе).

### 2. Модель не понимала аббревиатуры

Половина банковских доменных полей содержит аббревиатуры: БКИ, ОСЗ, ОСВ, СЭБ, КЗ, ЛСПР, ГО, ПДн, АМД, КТ, СКП, УАиГ, НА.

**Примеры расшифровок:**

| Поле | Было | Стало |
|---|---|---|
| `participant_app.bch_refuse` | «Отказ от БКИ» | «Флаг отказа участника-клиента от запроса в **БКИ (бюро кредитных историй)**. 1 = клиент отказал в запросе.» |
| `scp_amd_product.curr_loan_debt` | «Валюта ОСЗ» | «FK на валюту **остатка ссудной задолженности (ОСЗ)** по продукту.» |
| `offices_psb.feat_org` | «Признак: 1 - ГО» | «Флаг **головного офиса** (1 = головной офис, 0 = иное подразделение).» |
| `count_turnover.correct_type` | «Тип ОСВ» | «FK на справочник типа **ОСВ (оборотно-сальдовой ведомости)**. Различает виды ведомости (стандартная / корректирующая / специальная).» |

Эффект: при запросе «офисы только головной офис» или «остаток ссудной задолженности» модель теперь находит нужное поле — раньше она опиралась только на сокращения.

### 3. Модель не знала возможных значений булевых флагов

У флагов было только `0` / `1`, но без расшифровки модель не могла построить корректное `WHERE`.

**Примеры:**

| Поле | Было | Стало |
|---|---|---|
| `count_turnover.double_turn_balance` | «Дубликат» | «Признак дубликата записи ОСВ (**1 = дубль / исключить из агрегации, 0 = основная запись**). Используется для исключения дублей при подсчёте оборотов и сальдо.» |
| `credit_contract.hand_suspension` | «Ручная(мера)» | «Признак ручной приостановки договора (**1 = приостановлен оператором, 0 = активен**). Используется для фильтрации проблемных договоров.» |
| `participant_app.bch_refuse` | «Отказ от БКИ» | «Флаг отказа ... **1 = клиент отказал в запросе**.» |

### 4. Англоязычные описания в русскоязычной системе

В таблицах `sys_company` и `sys_employee` было несколько полей с английским описанием в overlay (Skype, Time zone, Photo, Website, Registrar, Tax authority) — это снижало релевантность для русскоязычных запросов и выбивалось из общего контракта v2.

**Пример:**

| Поле | Было | Стало |
|---|---|---|
| `sys_employee.skype` | «Skype» | «Логин Skype сотрудника (контактные данные). ... в SELECT — **только с маскированием**.» |
| `sys_employee.sys_image` | «Photo» | «FK на хранилище изображения профиля сотрудника (фотография). Используется в UI карточки сотрудника.» |
| `sys_company.date_of_consent` | «Дата согласия» | «Дата согласия клиента на обработку персональных данных (**152-ФЗ**). Используется в проверке актуальности согласия.» |

### 5. Дублирующиеся / legacy / тестовые поля без предупреждения

У некоторых таблиц есть колонки-дубли (`contracttype` vs `contract_type`), legacy-колонки с префиксом `_`, или тестовые поля. Раньше overlay не предупреждал об этом — модель могла одинаково выбирать обе колонки.

**Примеры:**

| Поле | Было | Стало |
|---|---|---|
| `credit_contract.contracttype` | «_Вид договора» | «Дублирующее техническое поле вида кредитного договора... Для новых выборок **предпочтительно `contract_type`**.» |
| `scp_collateral_app.testnumber` | «Тест_атрибут» | «Технический тестовый атрибут — служебное поле для проверок системы. **НЕ предназначено для бизнес-аналитики; не использовать в SELECT для отчётов.**» |
| `scp_project_ans.summ_tranche` | «_Сумма транша» | «Сумма транша по одобренному решению (в рублях). Префикс `_` указывает на дублирующее техническое поле; основное поле смотри в смежных таблицах.» |

Теперь модель видит явное предупреждение и предпочтёт правильное поле.

### 6. nl_phrases стали узкими

Раньше `nl_phrases` дублировали description: для `"description": "Сумма"` было `"nl_phrases": ["Сумма"]`. Это значит, что **одна и та же фраза «сумма»** в RAG-индексе вела в десяток колонок одновременно — recall высокий, precision нулевой.

В v2 после правки в `nl_phrases` всегда есть **объект** или **квалификатор**:

```json
"nl_phrases": ["сумма сублимита в карточке цены",
               "сумма по продукту ценообразования",
               "сублимит продукта в рублях"]
```

Эффект: запрос «сумма по продукту в карточке цены» хорошо матчит ровно в `product_pricing.scp_sublimit_sum`, не размазывается по 8 таблицам.

## Что НЕ улучшалось (граница ТЗ-01)

Чтобы ревьюер не искал — ниже намеренно не трогали:

- `category` колонок (key/filter/status/...) — это уже было корректно проставлено в v2.
- `pii_tags` таблиц — diff с v1 есть только в `sys_employee` (это правка PR #5), мы её не меняли.
- `approved_join_keys` — 0 различий vs v1.
- `allowed_ops` / `denied_ops` — 0 конфликтов.
- Имена таблиц и колонок — нельзя менять.
- Остальные ~1700 «нормальных» description (длиннее 16 символов и с минимальным контекстом) — это targeted, не massive rewrite.

## Найденные проблемы, которые надо передать дальше

1. **`scripts/validate_schema_overlay.py` не принимает `--path`** — TZ просит запускать его на v2, но скрипт хардкодит v1-путь. Нужна доработка в интеграционной ветке.
2. **`deploy/schema_overlay.schema.json` описывает только v1** (поле `columns` ему неизвестно) — поэтому формальная JSON Schema validation v2 валит на 60 ошибках. Это **pre-existing**, не следствие наших правок. Нужна schema v2.
3. **column.category="pii" vs table.pii_tags расхождение в `sys_employee`** — `email_confirmed`/`phone_confirmed` помечены `pii` на уровне колонки, но убраны из table-level pii_tags. Это security-review item для интеграционной ветки. Мы намеренно не трогали (граница ТЗ).
